# Daemon 与自恢复

IBL Rig 在 Raspberry Pi 5 上使用 systemd 和 ROS 2 共同管理整套系统。

可以把后台运行结构分成三层：

```text
开机常驻
├── 实验控制服务
├── 网页控制台
└── 网络状态监看

实验期间按需运行
├── C Board 控制
├── 时间同步
├── 诊断
├── 数据记录
├── 训练任务
├── OAK 相机
└── 刺激显示

实验结束后自动运行
├── 行为分析
├── NAS 上传
├── W&B
├── 飞书归档
└── 本地清理
```

这套结构把开机、实验运行和实验后处理分开管理。

## 开机常驻服务

### 实验控制服务

Pi 开机后，实验控制服务自动启动。

它负责：

- 保存当前实验状态
- 接收网页的实验请求
- 准备本次实验需要的设备
- 启动和停止设备服务
- 执行预检
- 汇总设备状态
- 管理暂停、继续、停止和中止
- 处理设备故障和恢复

systemd 会在这个进程异常退出后等待 3 秒并重新拉起。

### 网页控制台

网页使用 socket activation。

Pi 开机后先监听：

```text
0.0.0.0:18080
```

浏览器发起连接时，网页服务自动启动。

网页服务异常退出后，systemd 等待 2 秒重新启动。

网页状态保存在独立目录，实验配置目录和日志目录由 systemd 直接授权。

### 网络状态监看

网络状态监看服务持续观察配置好的远端节点，并通过飞书发送状态通知。

## 实验设备按需启动

进入视频预览或准备实验时，系统按照当前任务需要启动设备服务。

典型训练会用到：

- C Board 控制
- 时间同步
- 诊断
- 数据记录
- 训练任务
- OAK 相机
- 刺激显示

这些服务作为实验控制服务的子进程运行。

相机和刺激显示属于启动负载较高的设备。系统按顺序完成设备启动与状态确认，使 USB、显示和 CPU 初始化过程保持稳定。

实验结束后，对应设备服务进入空闲并退出。

## 服务状态和设备状态

后台服务持续发布两类状态。

**进程状态**

由 systemd 和设备服务管理器记录：

- running
- starting
- faulted
- restart count
- exit status

**设备状态**

由实际设备上报：

- OK
- WARN
- ERROR
- STALE

网页“预检”和实验状态使用设备状态作为运行依据。

## 中止与故障

网页中的 **中止实验** 是操作者主动结束当前训练的即时操作。

执行后：

1. 当前 Trial 记录为 aborted
2. 当前 Session 进入结束流程
3. Recorder 和相机完成收尾
4. 设备服务回到空闲/预览状态
5. 网页重新开放配置和预检

设备或系统异常进入故障锁存状态，并由对应恢复链处理。恢复完成后，操作者使用 **复位故障锁存** 清理故障状态，再执行预检。

## MCU 自恢复

系统持续读取 C Board 的状态。

当前恢复时间参数：

| 项目 | 当前值 |
|---|---:|
| 健康状态有效期 | 15 s |
| 连续异常后开始恢复 | 60 s |
| 最大连续恢复次数 | 3 |
| 恢复冷却 | 300 s |
| 稳定健康后恢复计数清零 | 60 s |

MCU 恢复分三级：

```text
Level 1
重新启动 MCU 控制服务
        ↓
Level 2
ST-Link / SWD 复位 STM32
        ↓
Level 3
复位 ST-Link USB
→ SWD 复位 STM32
→ 重新建立控制链路
```

每一级恢复结果都会写入运行日志。

硬件级恢复在实验空闲、实验结束或故障锁存状态执行。

故障锁存由网页中的 **复位故障锁存** 操作解除。

## OAK 自恢复

相机使用相同的健康监看机制。

恢复链：

```text
Level 1
重新启动相机服务
        ↓
Level 2
强制 USB 重新枚举
→ 重新建立 OAK pipeline
        ↓
Level 3
再次执行 USB 恢复
→ 重建 pipeline
```

相机录像结束后进入硬件恢复窗口。

视频预览请求会在故障状态下继续保留，使操作者可以直接观察相机恢复结果。

## 设备恢复后的操作

恢复完成后，网页会重新显示最新设备状态。

下一次实验按下面顺序进行：

1. 确认设备状态
2. 打开视频预览
3. 执行预检
4. 开始实验

## 实验后后台任务

一次实验完成后，后台队列自动产生数据处理任务。

流程：

```text
实验结束
   ↓
行为分析
   ├──→ W&B
   └──→ NAS
          ├──→ 飞书
          └──→ 本地清理
```

### 行为分析

生成：

- Trial 结果
- 正确率
- 奖励统计
- 时间统计
- 数据质量

### NAS

把本地 Session 文件复制到 NAS，并逐文件校验。

### W&B

上传训练参数、表现统计和质量指标。

### 飞书

生成实验索引，关联：

- 小鼠
- 操作者
- NAS
- W&B
- 数据质量

### 本地清理

NAS 校验完成后，本地 Session 进入自动清理队列。

## Path + Timer 双触发

后台任务使用两种触发方式。

**Path trigger**

任务队列目录发生变化时立即启动对应任务。

**Timer trigger**

定期再次扫描队列。

当前周期：

| 任务 | 定时扫描 |
|---|---:|
| 行为分析 | 5 min |
| NAS | 5 min |
| W&B | 5 min |
| 飞书 | 5 min |
| 本地清理 | 10 min |

这样任务既能在实验结束后立即开始，也能在网络或远端服务恢复后继续处理队列。

## 服务失败通知

实验控制服务和网页服务配置了 systemd failure notification。

服务进入失败状态时，独立通知任务会通过飞书发送：

- 服务名称
- 失败时间
- 状态信息

通知任务本身由 systemd 单独运行。

## 为什么这套结构稳定

每一层都有明确职责：

| 层 | 负责 |
|---|---|
| systemd | 开机、进程、权限、资源、崩溃重启、日志 |
| 实验控制服务 | 实验状态、设备服务启动、设备恢复 |
| C Board | Trial 实时执行、电机、泵、硬件安全 |
| 后台任务 | 分析、上传、归档、清理 |
| 网页 | 操作入口和状态展示 |

故障可以被限制在对应层内处理。

详细 unit 名称、启动方式和重启策略见 [Daemon Reference](/IBLRig/reference/daemons/)。
